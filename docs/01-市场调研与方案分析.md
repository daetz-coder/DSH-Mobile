# DSH-Mobile：市场调研与方案分析

> 目标：在手机 App 上"流转" DeepSeek Harness 的 Web 界面（控制对话、发起对话、查看输出），
> 采用"扫码配对 + 历史记录（免重复扫码）"模式，优先复用/二开现有开源项目，并与原生
> DeepSeek Harness 内容对齐。本文基于 2026-08 网络检索结果整理。

---

## 1. 结论速览（TL;DR）

1. **这个赛道已经有人做了，而且不止一家**。主流路线就是用户设想的两条：
   - **扫码配对 + 远程 Web 界面**（dsh-pocket / ds-harness-remote / orbis / mrgaoang-dsh-remote / xgone-dsh-remote）
   - **Hybrid App / WebView 壳 + 移动端适配**（dsh-web-mobile 及其移植、dsh-desktop 的 Electron 壳可作参考、Capacitor 方案尚未见成品）
2. **最值得二开的组合**（许可干净 + 活跃维护 + 与你需求完全重合）：
   - 电脑端插件：**dsh-pocket**（GPL-2.0，扫码即用、局域网 + 公网 cloudflared 隧道）或 **orbis**（Apache-2.0，E2E 加密、iOS 已上 TestFlight）
   - 手机端界面：直接白嫖 **dsh-web-mobile**（MIT，把 DSH Web UI 变成窄屏友好的抽屉/底部弹层）——它正是让"手机流转 Web 界面"好用的关键
   - App 壳：**Capacitor（Android/iOS 双端）** 包 WebView 加载远程 UI + 存储配对历史
3. **"对齐原生 DSH"的最优解不是重写 UI，而是复用官方 Web UI**：
   DSH 原生界面由 `@deepseek-ai/dsh-web-app`（`dsh web` 启动，127.0.0.1:3080，注入 `window.__DSH_BOOT__`）提供。
   手机端如果加载**同一套 Web UI**（WebView / 浏览器），功能对齐自动成立；
   而 sorsama/deepseek-harness-mobile 这种原生重写路线，要手工对齐 207+ 次 harness 提交的协议变化，维护成本极高——**不建议**。
4. **分发**：电脑端插件走 npm（`dsh plugin --profile web add <pkg>`，现有项目都这么做）；
   手机端走 APK / TestFlight / PWA。历史记录 = App 本地保存已配对端点（扫码一次，之后端到端加密免登录）。

## 3. 业务场景推演

### 3.1 用户的真实痛点与诉求
- DSH 长时间跑在自己电脑上（`dsh web` 只监听 127.0.0.1:3080，本机 GUI 即该服务）。
- 人离开电脑后，想在手机上：看 agent 干到哪、发新指令、点审批、切换会话——即"**把电脑上的 DSH Web 界面流转到手机**"。
- 不想每次重新配置：**扫码配对一次，之后记住（历史记录）**。

### 3.2 为什么"扫码配对 + 历史记录"是正确形态
1. **信任模型**：二维码里携带 `主机地址 + 令牌/公钥`。手机扫码 = 一次性完成"发现 + 授权"。
   - 局域网：`http://<PC-IP>:端口` 直连（dsh-pocket 就是这么干的）；
   - 公网：URL 换成 cloudflared 随机隧道地址，或经 relay/自建反代（ds-harness-remote、dshmobile、orbis 都是"双向加密通道 + 中继"）。
2. **历史记录**：App 把配对成功的端点存本地（token 用系统 Keystore 加密，sorsama 的做法）。
   下次打开直接连，无需扫码；列表支持"重连/移除/重扫"。
3. **安全红线**：DSH 能在电脑上执行代码，所以 URL/令牌就是钥匙，必须 E2E 加密 + 可吊销（隧道重启换 URL 即天然轮换）。

### 3.3 三条技术路线的对比

| 维度 | A. 纯 WebView（Capacitor + 远程 UI） | B. 插件 + 原生 App（orbis / remote 路线） | C. 原生重写 RPC（sorsama 路线） |
|---|---|---|---|
| 与原生 DSH 对齐 | ✅✅ 零成本，加载的就是官方 UI | ✅ 服务端是插件，UI 自研需对齐 | ❌ 需手工对齐协议（207+ 提交） |
| 开发成本 | 低（拼现成组件） | 中（要写 App + 协议） | 高（双端重写） |
| 原生能力（推送/相机/剪贴板） | 可经 Capacitor 插件桥接 | ✅ | ✅ |
| 上架商店 | ✅ APK/TestFlight | ✅ | ✅ |
| 维护负担 | 低（跟随官方 UI 升级） | 中 | 高 |
| 体验 | 良（依赖 dsh-web-mobile 适配） | 优（原生 UI） | 优 |

**结论：选 A（Hybrid WebView 壳）为主路线，B 的配对/加密设计作参照。**
这正好落回用户判断的"方案一扫码配对（主流）+ 方案二 Hybrid App 壳"——两者结合：
**扫码配对解决连接，Hybrid 壳解决"流转 Web 界面 + 历史记录 + 上商店"。**

## 4. 技术方案设计（二开蓝图）

### 4.1 总体架构

```
┌──────────────┐  扫码配对(Hybrid App 内相机)   ┌─────────────────────────────┐
│ Capacitor App │ ────────────────────────────→ │ 电脑端 DSH (dsh web :3080)   │
│ (Android/iOS) │  QR: 地址+令牌 (或 relay 公钥) │   ├ 官方 Web UI（原生界面）    │
│  ├ WebView 加载 │                              │   ├ 配对插件（二开 dsh-pocket）│
│  │  远程 Web UI │ ←── HTTP/WS/WebSocket ──── → │   │  ├ 局域网反代 + 扫码       │
│  │  (含 dsh-web  │    (E2E 加密通道)           │   │  ├ cloudflared 公网隧道    │
│  │   -mobile 适配)│                            │   │  └ 令牌签发/吊销           │
│  └ 历史记录(Keystore)│                         └─────────────────────────────┘
│     重连/移除/重扫  │
└──────────────────┘
```

### 4.2 复用清单（尽量不写新代码）

| 层 | 复用哪个项目 | 怎么用 | 许可注意 |
|---|---|---|---|
| 电脑端配对插件 | dsh-pocket（或其 proxy/tunnel 逻辑） | 直接装用；要自研就二开 `lib/proxy.mjs` + `lib/tunnel.mjs` + `bin/dsh-pocket.mjs` | GPL-2.0：二开后分发需 GPL |
| 电脑端配对插件（加密替代） | orbis / ds-harness-remote 的协议设计 | 若要求"账号体系 + E2E + 无需暴露 URL"，参考其 relay/通道设计 | orbis Apache-2.0 可参照；remote 无 LICENSE 不可抄代码 |
| 手机端 Web UI 适配 | dsh-web-mobile | 直接作为客户端插件加载（`dsh plugin --profile web add github:mexiaosqwq/dsh-web-mobile`）或把其 CSS/JS 打进 WebView 壳 | MIT，随便用 |
| 手机端 App 壳 | Capacitor（+ @capacitor-community/barcode-scanner 等） | WebView 加载远程 URL；扫码配对页；本地存配对历史 | 开源，随用 |
| 配对历史存储 | 参考 sorsama deepseek-harness-mobile 的 AndroidKeyStore + DataStore 模型 | 加密存 token，QR 的 code 可替换 typed code | MIT 参考 |
| 壳工程化样板 | dataelement/dsh-desktop（仅借鉴工程结构，不做 Electron） | 进程生命周期/日志/恢复 | MIT |

### 4.3 关键工程点（二开时最易踩的坑）

1. **特权方法受信任围栏限制**：`dsh web` 只把 loopback 来源当"本地"，
   插件式远程方案无法拿到 `settings.* / credentials.*` 等特权方法（mrgaoang 的表已证）。
   —— 如果只需要"发消息/看输出/点审批"，插件式够用；若要"远程改设置/管凭据"，需网关反代或本地代理（dsh-pocket 的改头反代）。
2. **WebSocket 全透传**：流式输出走 WS，反代必须支持 Upgrade 透传（dsh-pocket 已实现，直接参考）。
3. **移动端适配必须用 dsh-web-mobile 而不仅是 viewport meta**：官方 UI 是桌面布局，
   窄屏不改造会很难用；dsh-web-mobile v2.x 已处理抽屉/安全区/触控/输入区重叠/兼容 dshmarket。
4. **公网出网**：cloudflared 快速隧道（dsh-pocket 方案）简单、URL 随机轮换；
   但注意本机代理/VPN（Clash TUN 等）会掐断隧道（dsh-pocket README 有完整排障）。
   稳定商用可自建 relay（参考 dshmobile 的 relay/ 目录或 ds-harness-remote 中继）。
5. **版本对齐**：本机 DSH 为 0.1.0-rc.7；生态最新基线 0.1.1-rc.2。
   dsh-web-mobile 的 peer 范围是 `^0.1.0-rc.6 || >=0.1.1-rc.0 <0.2.0`，本机可用。
   升级 dsh 前先查配对插件的兼容声明（dsh-pocket 要求重启 dsh web 才生效）。

### 4.4 分步落地计划（建议）

- **M0（半天）**：本机装 `dsh pipeline --profile web add dsh-pocket` → 重启 → 手机浏览器扫码验证局域网/公网可达。
  同时手机浏览器加 `dsh-web-mobile` 看窄屏效果。（验证"现成方案是否已满足 80% 需求"）
- **M1（1-2 天）**：Capacitor 空壳（Android + iOS），WebView 加载远端 UI + 扫码配对页 + 配对历史（Keystore 加密）。
- **M2（1-2 天）**：接入 dsh-web-mobile 适配 + 原生增强（剪贴板、振动、通知/角标、下拉刷新、断线重连）。
- **M3（按需）**：二开 dsh-pocket 补"令牌化配对 + 多设备 + 吊销"；或换 orbis 路线做 E2E 加密 + 自建 relay。
- **M4**：分发——插件发 npm（`dsh plugin --profile web add dsh-mobile-<name>`），
  App 发 Android APK/AAB + iOS TestFlight/App Store，附 PWA 降级路径（仅浏览器也能用）。

## 5. 分发与商业考虑

### 5.1 分发渠道
- **电脑端插件 → npm**：生态标准做法（dsh-pocket / ds-harness-remote / @orbisapp/remote-dsh / @zdx8637/dshmobile-bridge 都是 npm 包），一条命令安装。
- **手机 App → APK + App Store/TestFlight**；同时保留 Web/PWA 入口（remote web launcher 思路，liguobao 已有 `dsh.r2049.cn/app`）。
- **隧道/中继**：免费 cloudflared（个人自用）；商用自建 relay。

### 5.2 许可证决策树（重要，别踩坑）
- 若**个人/开源分发**：GPL-2.0 的 dsh-pocket 可直接二开（改版必须开源同许可）。
- 若**商用闭源**：
  - ✅ 用 MIT/Apache 组件：dsh-web-mobile、zdx8637/dshmobile、xgone/dsh-remote、orbis（Apache-2.0）、dataelement/dsh-desktop、sorsama/deepseek-harness-mobile
  - ⚠️ dsh-pocket（GPL）：可整包使用（不修改不构成衍生？建议咨询），二开则需开源；或自研等价 proxy/tunnel
  - ❌ liguobao/deepseek-harness-remote：仓库无 LICENSE = 默认保留版权，不可商用二开（仅作架构参考）
  - ⚠️ mrgaoang/dsh-remote：PolyForm 非商业，商用需买授权
- **改版 GPL 组件的替代**：自己写 proxy/tunnel（约 300-500 行，dsh-pocket 架构文档已把要点写清楚，可"参考其 API 行为、不复制代码"规避）或直接商业授权。

## 6. 待确认 / 下一步

1. 确认目标平台范围：**Android 先行**（生态里 Android 最成熟）还是双端？
2. 确认网络诉求：仅**局域网**够用，还是要 **4G/公网**（决定要不要 cloudflared/relay）？
3. 确认是否需要**远程特权操作**（改设置/管凭据）——影响选插件式还是网关式。
4. 上架诉求：个人分发（GitHub Release/APK）还是上应用商店（需要开发者账号 + 签名）？
5. **是否允许基于 GPL（dsh-pocket）二开并开源**，还是要求纯 MIT/Apache 组合（推荐先跑通 M0 现成方案，再定）。

> 建议：**先跑 M0**（装 dsh-pocket + dsh-web-mobile 验证现成方案），几乎零成本就能确认"手机流转 DSH Web 界面"的体验下限；
> 之后所有二开工作都在这条已通的链路上增量叠加。
